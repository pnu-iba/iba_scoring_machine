# 007 — 팀 식별과 제출 한도 강제 방식

결정일: 2026-09-21

## 질문

"팀당 하루 3회"를 강제하려면 서버가 제출자를 팀 단위로 신뢰성 있게 알아야 한다. 어떤 방식으로 팀을 식별할 것인가?
(a) 운영자가 기수 시작 시 팀별 제출 코드(토큰)를 발급하고, 제출 시 코드를 입력 — 로그인 없음.
(b) 팀원이 각자 학교 이메일/Google 계정으로 로그인하고, 운영자가 계정을 팀에 배정.
(c) 자유 가입 + 팀명 자기 신고 — 제한 우회가 쉬움.
(d) 사이트 자체 계정(아이디·비밀번호) — 가입할 때 팀명을 적고, 제출은 로그인한 계정의 팀으로 기록.

## 지금 정해야 하는 이유

004에서 제출 제한과 리더보드 항목은 정해졌지만, 식별 방식이 없으면 제한은 장식이 된다. 또한 이 답이 006의 인증 구성(로그인 라이브러리·세션 저장소 필요 여부)을 결정한다. (a)는 저장소 한 테이블로 끝나고, (b)는 OAuth·세션이 추가된다.

## 근거 자료

- 004 결론: 리더보드에 닉네임과 팀명을 함께 표시 → 제출 시 닉네임(개인)과 팀(집단) 두 층위가 모두 필요함. (a)에서는 코드가 팀을, 입력 필드가 닉네임을 담당할 수 있음.
- 동아리 규모(기수당 팀 수·인원)는 아직 미기록 → 질문 시 확인. 팀이 10개 안팎이면 (a)의 수동 발급 부담은 작음.
- 이용자가 모두 동아리원(신뢰 집단)이라 부정행위 방지 수준은 "실수 방지 + 가벼운 억제"면 충분할 가능성이 높음.

## 결론

(2026-09-21, 사용자 결정) **(d) 자체 계정.** 아이디·비밀번호로 가입하고, 가입할 때 팀명과 닉네임을 적는다.

- 가입은 누구나 할 수 있다(가입 코드 없음). 제출과 남은 횟수 조회만 로그인이 필요하고, 홈·리더보드·미니게임은 로그인 없이 본다.
- 팀은 가입 때 적은 팀명의 정규화 문자열로 묶인다. 같은 팀명을 적은 사람끼리 한 팀이고, 하루 3회는 팀 단위로 센다. 리더보드의 팀 표기는 그 팀으로 처음 가입한 사람의 표기를 따른다.
- 받아들인 위험: 가입할 때 남의 팀명을 적으면 그 팀에 들어가 횟수를 나눠 쓰게 된다. 이용자가 모두 동아리원이라 규칙·신뢰로 막고, 운영자는 제출 삭제로 바로잡는다. 가입 후 팀명 변경과 비밀번호 재설정 기능은 없다.
- 제출 때 팀명·닉네임을 다시 입력하지 않으므로 오타로 새 팀이 생기는 문제는 가입 시점 한 번으로 줄어든다.

## 이후 영향

- 006: 외부 인증 서비스 없이 FastAPI 안에서 처리한다. 비밀번호는 PBKDF2 해시로 `users` 테이블에 두고, 세션은 서버 저장소 없이 HMAC 서명 쿠키로 유지한다. 비밀값 환경변수가 하나(`SESSION_SECRET`) 늘어난다.
- 개인정보는 아이디·닉네임·팀명만 받는다. 이메일·실명은 받지 않는다.
- 운영자용 제출 삭제 수단(관리자 키로 보호된 최소 기능)은 그대로 필요하다.

## 구현에서 달라진 점

- 팀은 팀명이 아니라 숫자 팀 번호로 묶는다. 가입은 `scoring/teams.py`의 `TEAMS`에 있는 이번 기수 팀 번호 1-4만 받는다.
- 관리자가 관리자 페이지에서 학생의 팀을 옮기고 임시 비밀번호를 발급할 수 있다. 학생이 직접 팀을 바꾸거나 비밀번호를 재설정하는 기능은 없다.
- 남의 팀 번호로 가입하는 위험은 그대로 받아들이고, 운영자가 제출 삭제와 팀 이동으로 바로잡는다.
